# ADR-005: activity-catalog v0.2 schema design

**Date**: 2026-04-05
**Status**: Accepted

---

## Context

The catalog schema defines the public distribution format consumed by LLMs, XAML
generators, documentation tooling, and human readers. It is derived from PackageFurnace
engine-result files by the catalog pipeline (`build_dist.py`).

v0.1 was a single merged file for a named set of packages. v0.2 was redesigned from
the ground up after a consumer audit (cpmf-uips-xamlgen) identified missing fields,
ambiguities, and structural mismatches. The decisions below record the v0.2 shape and
the reasoning behind each choice.

---

## Decisions

### One package = one catalog file (per-package as primary artifact)

Each catalog file covers exactly one `(packageId, version)` pair. A per-package file
is independently addressable, cacheable, and versionable. Sets are a derived convenience,
not the primary unit.

v0.1 merged all packages into one file per set. That made the file the primary artifact
and the package secondary — the reverse of the intended ownership model.

### Set: JSON array with metadata header at position 0

A catalog set is a JSON array. The first element `[0]` is always a set-level metadata
object (identified by the `metadata` key). Elements `[1..n]` are inlined per-package
catalogs conforming to the per-package schema.

An object wrapper (`{ "metadata": ..., "catalogs": [...] }`) was considered but
rejected: the array form makes streaming consumption natural and avoids a nesting level.
The distinguishing rule (presence of `metadata` key vs. `source` key) is explicit in
the schema description.

### source at catalog level, not per activity

`source` (package identity and metadata) appears once at the catalog root, not repeated
on every activity. Activities within a catalog all share the same source by definition.
This avoids redundancy while keeping the `activity.id` field (`{fullName}@{source.id}/{source.version}`)
self-contained for cross-catalog references.

### activity.id matches PackageFurnace engine-result id format

`activity.id` uses the same `{fullName}@{sourceId}/{sourceVersion}` format as the
engine-result. This allows consumers to correlate catalog entries back to engine-result
records without a separate lookup table.

### enrichment: null | object extension point

Each activity carries an `enrichment` field typed `object | null`. It is `null` when
no human-authored enrichment has been applied. The internal structure of `enrichment`
is defined by the enrichment pipeline and is intentionally left open in this schema.
This avoids coupling the catalog schema to the enrichment schema version.

### synthetic source kind (catalog-only)

`source.kind` includes `"synthetic"` for hand-authored catalog entries not produced by
PackageFurnace. Synthetic entries are used for gap analysis and activity design planning.
XAML generators must treat synthetic-sourced activities with caution: `namespaceMappings`
may be absent or partial, and output cannot be verified against a real assembly.
Generators should emit a warning diagnostic when encountering synthetic sources.
Synthetic activities are not intended for production XAML generation.

### Hidden activities filtered at transform time

Activities with `visibility: "hidden"` are excluded by the catalog pipeline. The
catalog schema's `visibility` enum contains only `"browsable"` and `"legacy"` — hidden
is not a valid value here. Filtering is a pipeline responsibility, not a schema concern.

### member.displayName: required, non-nullable, guaranteed by pipeline

`member.displayName` is `type: string` (non-nullable, required). The extraction pipeline
(`MetadataNormalizer`) always emits a value: when no `DisplayNameAttribute` is present on
the CLR property, it falls back to the CLR property name. This guarantee is documented
in the property description. The non-nullable type is intentional and correct.

`activity.displayName` is nullable because no such fallback exists at the activity level
— an activity with no display attribute emits `null`.

### member.dataType: nullable string (null = absent in source)

`member.dataType` is `type: ["string", "null"]`. A `null` value means the CLR property
had no resolvable type in source. Empty string is not used — it is not a valid CLR type
name and cannot be distinguished from a real empty-named type by schema validation.

The pipeline (`build_dist.py`) passes `null` through rather than coercing it to `""`.

### argumentDirection: documented WF4 CLR type mapping

`argumentDirection` values map to WF4 CLR argument wrapper types:

- `"in"` → `System.Activities.InArgument<T>`
- `"out"` → `System.Activities.OutArgument<T>`
- `"in-out"` → `System.Activities.InOutArgument<T>`

This mapping is documented in the property description so XAML generators do not have
to infer it from convention.

### namespaceMappings: deduplication and set-merge semantics specified

Within a single catalog, entries are deduplicated by `(xmlNamespace, sourceAssembly)`.
When consuming a set (multiple catalogs), consumers must merge namespace mappings:

- **Prefix assignment**: first occurrence of each `xmlNamespace` across catalogs wins.
- **clrNamespaces**: lists are per-catalog and are not merged across catalogs.

These rules give consumers a deterministic strategy without requiring a central registry.

### Enum casing: all values kebab-case

All enum values in this schema use kebab-case (`"browsable"`, `"legacy"`, `"in"`,
`"out"`, `"in-out"`, `"argument"`, `"variable-scope"`, `"child"`, `"property"`,
`"nuget-package"`, `"dotnet-runtime"`, `"local-path"`, `"synthetic"`). This is
consistent with the PackageFurnace engine-result schema, which applies
`JsonNamingPolicy.KebabCaseLower` globally.

---

## Consequences

- A catalog set and its per-package catalogs are independently versioned. Adding a
  package to a set means adding a catalog file; the set file references it inline.
- The `enrichment` field is an open extension point. Its internal schema is defined
  elsewhere and evolves independently.
- Consumers must handle `member.dataType = null` and must not treat empty string as a
  sentinel.
- `member.displayName` is always safe to use as a display label without null-checking.
- XAML generators must implement the `namespaceMappings` merge rule described above
  when consuming sets; per-catalog consumption requires no merge.
